# 工具编排与多Agent协同

## 核心要点
- 编排的核心是**分解**——复杂任务先拆成依赖图，再决定由谁跑哪块
- 不是Agent越多越好；一巨兽50工具不如5个单职责Agent（174反模式2）
- 共享状态=毒药——Agent该各自拥有文件/资源，重叠处用锁
- 每次spawn子Agent前先想："这是任务真的需要隔离，还是我只是想偷懒把上下文切走？"

## 五大经典编排模式

### 1. 顺序管道（Sequential Pipeline）
```
A → B → C
每个步骤的输出是下一步的输入；适合编译/生成类任务
坑：A失败=全流程卡死 → 解药：B入口加输入有效性检查
```
### 2. 并行发散/汇聚（Fan-out/Fan-in）
```
     ┌→ B1
A ──┼→ B2
     └→ B3
      ↓
     C（汇总）
```
- 适合：多角色同时处理的场景（如"同时生成3个分镜版本"）
- 坑：B1/B2/B3结果格式不一致 → 解药：正文写死输出模板（173），C用模板字段合并而非自由文本

### 3. 层级委派（Hierarchical Delegation）
```
主Agent: 规划 → 拆解 → 分发
  ├─ 子Agent A: 执行块1
  ├─ 子Agent B: 执行块2
  └─ 子Agent C: 验证结果
```
- 适合：大项目（如整集动漫短剧从剧本到成片）
- 主Agent只干两件事：**拆任务 + 合结果**，不亲自执行细节

### 4. 事件驱动（Event-driven Reactors）
```
文件变更 → 触发Agent A
用户输入 → 触发Agent B
定时器   → 触发Agent C
```
- 适合：监听/自动化类skill（如实时会议转录、文件同步）
- 坑：事件风暴——高频事件压垮Agent → 解药：去抖动/批处理

### 5. 共识验证（Consensus Validation）
```
输入 → Agent A生成 → Agent B审核 → Agent C拍板
```
- 适合：高敏感输出（如安全扫描、财务计算、法律建议）
- 三个Agent可以独立调用，也可以由主Agent顺序调度

## 编排铁律

| 原则 | 含义 | 违反代价 |
|---|---|---|
| 分解先行 | spawn前画出依赖图 | 步骤串行变乱序 |
| 最小共享 | Agent各自拥有文件 | 状态冲突/覆盖 |
| 工具目标导向 | "用适合的工具完成"而非"先调A再调B" | 环境一变全崩 |
| 优雅失败 | 每步都要有重试/回退/降级方案 | 单点故障毁全局 |
| 预算意识 | token/时间/API调用有上限意识 | 账单爆炸/超时 |

## 正文里怎么写编排
```markdown
## 多Agent执行步骤

1. 分析用户需求，拆为：[子任务A] [子任务B] [子任务C]
2. 对A/B/C各自spawn子Agent，描述中写明：
   - 该Agent的role（如researcher/builder/validator）
   - 需要的上下文文件
   - 成功标准
3. 等待全部完成 → 汇总到 summary.md
4. 主Agent做最终检查和输出
```
- 参考本机实际：`h3-fight-storyboard`调用`hik-scanner-package`等skill的格式

## 权限最小化
```yaml
# 好的声明
permissions:
  filesystem: read      # 只读配置
  shell: restricted     # 白名单命令
  
# 坏的声明
permissions:
  filesystem: write     # 不需要写的也声明
  shell: unrestricted   # 全部shell权限
```
- 过度授权=信任崩塌+review时被毙掉（174反模式5）

## 常见坑
- **串行思维陷阱**：所有任务都排成一条链=浪费并行机会，没算依赖图
- **微Agent滥用**：3行shell命令也spawn一个Agent=上下文切换开销爆炸
- **无明确成功标准**：子Agent跑完不知道"done"长什么样（174反模式7）
- **Stateless幻觉**：以为多轮对话能记住一切=中间状态丢了全靠脸
- **工具链硬编码**：把顺序写成正文铁律，环境一换全白干（174反模式4）

## 进阶
- **中间产物落盘**：每步结果写到work/，失败时恢复/审计——参考177流程型skill的checkpoint设计
- **动态路由**：主Agent先分类→再根据分类spawn不同子Agent，而不是一个万能Agent
- **回退链**：首选方案A失败→自动降级到方案B→再失败到方案C→人工介入
- **成本路由**：复杂任务先给轻量模型，失败/困难再升级到强模型
- **日志埋点**：主Agent维护执行日志（用时/步数/失败次数），事后复盘

## 备注
- 五大模式：顺序/并行/层级/事件驱动/共识验证
- 编排铁律：分解/最小共享/目标导向/优雅失败/预算意识
- 权限最小化是信任的基础
