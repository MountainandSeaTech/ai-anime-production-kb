# 个人Skill体系设计——从散装到编队

## 核心要点
- 散装skill=消耗品（用完即弃），编队skill=资产（越用越值钱）
- 体系设计的核心回答三个问题：**我有哪些能力？能力之间什么关系？新能力往哪放？**
- 好的体系让skill自己长出来——用户要X，你一看地图就知道是新建还是复用还是扩展

## 体系分层

### 按抽象层级分
```
L1 - 原子能力（不可再拆）
     例：读文件/写文件/调API/查数据库
     
L2 - 领域能力（特定场景）
     例：PDF处理/视频生成/分镜编排/音频合成
     
L3 - 工作流能力（跨领域编排）
     例：动漫短剧全流程/会议纪要整理/代码审查流水线
     
L4 - 元能力（管理其他skill）
     例：skill创建器/能力地图生成器/维护巡检器
```
- 新skill先定位层级——L1是工具，L2是武器，L3是战术，L4是兵法

### 按使用频率分
```
高频（每周>3次）→ 重点维护，放最顺手位置
中频（每月1-3次）→ 标准维护
低频（季度/年度）→ 归档备用，别删
```
- 频率决定维护资源分配——别给一年用一次的skill配每周巡检

## 命名与组织规范

### 目录结构
```
skills/
├── 01-写作/           # 领域分类
│   ├── xuanhuan-novel-writer/
│   ├── daily-comedy-writer/
│   └── ...
├── 02-视频/
│   ├── h3-fight-storyboard/
│   └── ...
├── 03-工具/
│   ├── hik-scanner-package/
│   └── ...
└── README.md          # 体系地图（本条目就是干这个的）
```

### 命名规范
```
格式：[领域前缀]-[功能]-[类型]
示例：
  h3-fight-storyboard      # H3打戏分镜
  hik-scanner-package      # Hikvision扫描打包
  lark-doc                 # Lark文档操作
  
禁止：
  MySkill / test123 / new-skill / skill-final-v2
```
- 名字即域名——见名知意，不用点进去看

## 能力地图（Capability Map）

### 场景→能力对照表
```
用户要"写玄幻小说"
  → xuanhuan-novel-writer（L2）
  
用户要"写玄幻小说并生成动漫短剧"
  → xuanhuan-novel-writer（剧本）
  → h3-fight-storyboard（分镜）
  → anime-director（视频生成）
  → 组合成L3工作流

用户要"写个skill来自动化XX"
  → skill-creator（L4元能力）
```

### 依赖图谱
```
anime-director
  ├── depends: h3-fight-storyboard（分镜资产）
  ├── depends: volcengine-cli（视频生成API）
  └── used-by: 用户直接调用
  
skill-creator
  ├── depends: 无（自举）
  └── used-by: 所有需要新skill的场景
```
- 改skill前先查依赖——改了A，谁会被波及？

## 知识库与Skill的共生（176的升级版）

```
知识库（176）= 静态资产（学了存着）
Skill（171-175）= 动态能力（存了能用）

循环：
学习 → 沉淀到知识库 → 需要时封装成skill → skill调用知识库条目 → 产出新经验 → 沉淀回知识库
```
- 知识库是skill的弹药库，skill是知识库的投射器
- 本知识库170+条目=未来skill的原材料储备

## 扩张策略：什么时候新建vs扩展

| 信号 | 决策 |
|---|---|
| 新需求和现有skill差异>70% | 新建 |
| 新需求是现有skill的自然延伸 | 扩展现有 |
| 新需求和现有skill有交集但场景不同 | 抽公共部分成新skill，两者依赖它 |
| 现有skill臃肿（>500行正文） | 拆分 |

## 常见坑
- **重复建设**：不查现有skill直接新建=能力碎片化，维护噩梦
- **过度抽象**：为"未来可能的需求"设计L4元能力=过度工程，实际需求来了发现抽象错了
- **命名混乱**：`my-skill`/`test`/`new`/`final`混用=三个月后自己都不认识
- **无地图导航**：skill多了之后"我记得有个skill能做这个但找不到"=需要能力地图（181）
- **僵尸skill**：写了从不维护也不归档=体系里的腐肉（179）

## 进阶
- **能力雷达图**：定期评估各领域覆盖度（写作/视频/音频/工具/流程），发现短板
- **组合技预研**：哪些skill组合起来能产生1+1>2的效果？（如写作+分镜+视频=全自动短剧）
- **对外接口**：高频skill暴露API/CLI，让其他工具/脚本也能调用
- **版本对齐**：依赖同一底层服务的skill保持版本同步，避免接口漂移
- **体系自检**：每季度跑一次"能力覆盖审计"——用户最近要什么？我有没有？缺在哪？

## 备注
- 四层体系：原子/领域/工作流/元能力
- 场景→能力对照表是导航核心
- 知识库↔skill形成沉淀-调用循环
- 扩张四原则：新建/扩展/抽取/拆分
