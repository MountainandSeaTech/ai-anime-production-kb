# 流程型Skill——确定性任务的执行引擎

## 核心要点
- 流程型skill的目标是**任务完成**，不是知识积累——从状态A到状态B的确定性转换
- 和知识型skill（176）正好相反：它产生消耗，不追求复用
- 核心追求：**可预测、可审计、可回滚**——每一步都有明确的before/after

## 适用场景
```
✅ 把XX文件批量转成YY格式
✅ 按模板生成视频并输出到指定目录
✅ 从A仓库提取数据写入B数据库
✅ 运行测试套件并汇总报告
✅ 部署流程：拉取→构建→验证→上线

❌ "帮我学习一下XX领域" → 这是知识型
❌ "帮我写个关于XX的思考" → 这是开放式对话
```

## 流程设计的四定原则

| 原则 | 含义 | 检查项 |
|---|---|---|
| 定入口 | 输入必须满足什么条件 | 格式/字段/大小/权限 |
| 定步骤 | 每步做什么、用什么工具、产什么文件 | 编号、动词、产物路径 |
| 定出口 | 怎么算完成 | 产物存在/验证通过/用户确认 |
| 定异常 | 每步失败怎么处理 | 重试/降级/回滚/报错 |

## 状态管理与Checkpoint

### 中间状态落盘（174反模式6的解药）
```markdown
## 工作目录结构
workflow/
├── step1-input/       # 原始输入（只读）
├── step2-processed/   # 处理产物
├── step3-validated/   # 验证通过产物
└── log.txt            # 执行日志
```
- 不要把状态寄存在对话上下文里——对话一长就丢
- 每完成一步写checkpoint文件：日期+状态摘要=失败时可精准续跑

### 可恢复执行
```markdown
## 续跑逻辑
1. 检查 workflow/log.txt 最后一条记录
2. 若已完成到step3 → 跳过1-3，从step4继续
3. 若step2失败 → 重试step2，保留step1结果
```
- 长流程必须支持断点续传——否则跑一次要命的活不能重来

## 正文骨架（流程型专用）
```markdown
# Skill名称

## 入口校验
检查输入格式/字段/权限；不满足则立即报错，不猜。

## 步骤 1：XXX
- 输入：来源路径/数据
- 动作：具体工具调用
- 产物：写到指定路径
- 失败：重试X次/降级到方案Y

## 步骤 2：XXX
...同上...

## 出口验证
对照标准清单检查产物；不通过不交付。

## 清理
删除中间临时文件（保留log和最终产物）
```

## 与知识型的对比

| 维度 | 流程型 | 知识型（176） |
|---|---|---|
| 产出 | 状态变化/文件/部署 | 可复用知识条目 |
| 时间 | 单次会话 | 跨会话复用 |
| 失败 | 任务未完成，需回滚 | 质量不够，可重加工 |
| 验证 | 出口验收标准 | 是否被后续任务引用 |
| 存档 | 产物+日志 | 条目+索引 |

## 常见坑
- **流程太长不拆分**：15步的流程写成一个skill=任何一步出错全崩（175的层级委派救场）
- **不校验入口**：用户给个空文件，流程跑到第7步才发现=前6步白跑
- **产物不验证**：跑完就算成功，输出是错的不知道——出口必须有自动化验收
- **清理过头**：临时文件删了=无法审计/无法续跑——只删真·垃圾，保留log
- **状态混用**：流程型和知识型写成一个skill=四不像，调用逻辑混乱

## 进阶
- **幂等设计**：同一输入跑两遍=同一结果，不重复副作用——适合重试和续跑
- **日志结构化**：每条log含[时间/步骤/结果/耗时]，方便事后排查和成本核算
- **参数化配置**：把可能变的值（路径/阈值/超时）抽成变量，不硬编码
- **通知钩子**：关键步骤完成后发通知（IM消息/邮件/标记），不用人盯着等
- **熔断机制**：连续N步失败→自动暂停→转人工/报警，不要无限重试

## 备注
- 四定原则：定入口/定步骤/定出口/定异常
- 中间状态落盘，支持断点续传
- 流程型和知识型分家，不要混用
